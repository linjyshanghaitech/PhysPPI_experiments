# PDB Cache 交接文档 — 2026-07-28

## 我们在做什么

**目标**：把 PhysPPI 训练中每个 sample 的 PDB 解析 + 原子标准化（去 H、MSE→MET、FME 修正、CCD canonicalize）
离线完成，存为 `.pt` 张量文件。训练时 `torch.load` 直接拿到 `biotite.structure.AtomArray`，
**跳过全部 PDB 文本 I/O 和原子归一化**。

PhysPPI 训练 pipeline 每 sample 做这些事：
1. `parse_pdb_af2()` 文本解析 GT PDB + 多个 monomer PDB → `AtomArray`
2. `_canonical_ppi_heavy_atom_array()` 重原子标准化
3. `_annotate_canonical_mol_entity_ids()` entity ID 标注
4. Monomer 还要 `process_target_atom_array_of3` (no-crop) + `add_token_positions`

这些都是纯确定性操作（只依赖输入文件和 CCD），每个 epoch 重复做纯属浪费。

**pdb_cache** 每 sample 生成 3 类 `.pt`：

| 文件 | 内容 | 处理深度 |
|------|------|---------|
| `{case_id}_gt.pt` | GT PDB canonized AtomArray (complex coords) | 停在 `process_target_atom_array_of3` 之前，保留 crop 在线做 |
| `{case_id}_{chain}_monomer.pt` | Monomer PDB processed AtomArray (monomer-local coords) | 完整处理（含 no-crop process + token_positions） |
| `{case_id}_seq.pt` | seq_cache 序列元数据 | 从 chunk 级 `seq_cache.pkl` 按 sample 提取 |

**收益**：每个 sample ~350-750ms → ~15-30ms（~20-50× 加速），且与已有 mesh/residue prior 统一用 `.pt` 格式。

### 4. 三种 `.pt` 格式

GT `.pt` 保存 **20 annotations**（per-atom 数组）：`chain_id`, `res_id`, `res_name`, `atom_name`, `coord`, `element`, `entity_id`, `mol_entity_id`, `molecule_type_id`, `occupancy` + PDB 元信息。

Monomer `.pt` 保存 **30 annotations**：同上 + `token_id`, `token_position`, `is_atomized`, `crop_mask`, `mol_sym_id`, `mol_sym_component_id`, `mol_sym_token_index` 等。

Seq `.pt`：`full_seq_1aa`, `full_seq_3aa`, `resseq_to_sequence_index`, `mask`, `msa_eligible`。

**残基复原不需要额外 index**：`biotite.structure.get_residue_starts()` 扫描 `res_id` + `chain_id` 自动找边界。
**原始 PDB 残基号原样保留**：`res_id` 不重编号（Q-BioLiP `1a0s_1` 从 71 开始，`res_id` 就是 71）。

详见 `README.md` 完整展开。

## 踩过的坑——绝对不要再踩

### 1. 不能只存 CB/CA 原子（最坑）

Monomer `.pt` 必须保存 **完整 backbone 原子（N, CA, C, O）**，不能精简到只存 CB 或 CA。

根因：`build_monomer_input_geometry()` 做 per-atom 三元组查表 `(chain, resseq, atom_name)`，
GT 的每个 N/C/O 都要在 monomer lookup 里找到对应坐标。
只存 CA → GT 的 N、C、O 全查不到 → `monomer_mask` 大面积 False。

更致命的是末尾的代表性原子校验：每个 chain 需要 ≥4 个有限非共线点。
只存 CA → 每残基仅 1 个坐标 → 全链 CA 沿 backbone 大致共线 → `matrix_rank < 2` → `PhysPPIDataError("missing_mandatory_monomer_geometry")`。

**结论**：monomer `.pt` 存完整 AtomArray 通过 `save_atomarray_as_pt`。

### 2. String annotation dtype 必须保留

`save_atomarray_as_pt` 最初把字符串 annotation 转成 Python list（`.tolist()`），
导致 `auth_asym_id` dtype 从 U4 变成 U1（numpy 自动推断），round-trip 失败。

**修复**：所有 annotation 直接保存为 numpy ndarray（`torch.save` 用 pickle 内部处理），
dtype 完全保留。`load_atomarray_from_pt` 用 `atom_array.set_annotation(key, val)` 原样恢复。

### 3. `_runtime.py` import 会导致 CUDA 库依赖链

`generate_pdb_tensors.py` 最初 import `_runtime.py` → `base_of3.py` → ... → 模型层 → `cuequivariance_ops` → `libcublas.so.12` 缺失 → crash。

**修复**：生成脚本不 import `_runtime.py`，而是把 `_canonical_ppi_heavy_atom_array`、`_annotate_canonical_mol_entity_ids`、`_chain_metadata`、`_restrict_gt_atom_array_to_sample` 的逻辑 inline 重写。代价是如果上游这些函数的逻辑变了，生成脚本需要手动同步。

### 4. Sample 级多进程（`Pool.imap_unordered`）会 hang

`multiprocessing.Pool` 配合 sample 级 `imap_unordered` 在 64 workers 下 hang 住不产出。
改为 **chunk 级 `ProcessPoolExecutor`**（一个 worker 处理一个完整 chunk，串行遍历其中 sample），
与 `residue_prior/generate_residue_tensors.py` 的并行模式一致，顺利跑通 64 workers。

### 5. AFDB 不需要 CCD，Q-BioLiP 需要 CCD

AFDB 全部是标准 20 氨基酸 + MSE（自动转 MET），reference mols 的 21 个 SDF 全覆盖。
Q-BioLiP 有大量化学修饰残基（FME、SEP、TPO、M3L、PCA、BFD...），
不在 reference mols 里，`remove_non_CCD_atoms` / `canonicalize_atom_order` 必须 CCD。

CCD 是惰性加载的（`_resolve_ccd()` 只在 `_needs_ccd()` 返回 True 时才读 483MB 的 components.cif）。

### 6. `_AA3_TO_1` 不能只用 20 氨基酸

最初写了硬编码的 20 氨基酸映射，用户指出必须用 `physppi_prior.aa_map.AA_MAP`（1033 entries）。
生成脚本现在 `try: from physppi_prior.aa_map import AA_MAP`，失败时才 fallback 到 20 氨基酸。

需要额外添加 `/101045/jinyu/PPI/Prior/src` 到 `sys.path`。

### 7. Monomer PDB `process_target_atom_array_of3` 需要 entity_id

`process_target_atom_array_of3` → `assign_mol_permutation_ids` → `assign_mol_symmetry_ids` → `get_precursor_entity_ids`
会检查 `entity_id` 或 `mol_entity_id` annotation。没有的话直接 `ValueError`。

**修复**：inline 的 `annotate_entity_ids()` 必须在 `process_target_atom_array_of3` 之前调用。

### 8. `nohup` stdout 缓冲导致 log 为空

`nohup python ... > log 2>&1 &` 后 `tail -f log` 长时间看不到输出，以为进程挂了。
实际 Python stdout 在 nohup 下默认全缓冲（不是 line-buffered），只有进程结束或 buffer 满才会刷盘。

**用 `stdbuf -oL` 或 `PYTHONUNBUFFERED=1` 可以解决**，但这次没加，导致多次误判进程 hang。
