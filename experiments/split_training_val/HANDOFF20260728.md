# Train/Val Split 交接文档 — 2026-07-28

## 我们在做什么

**目标**：将 PhysPPI 的训练数据（AFDB 10,000 + Q-BioLiP 10,021 = 20,021 个 complex）
按 **AlphaFold-Multimer 的 chain-level homology 协议**拆分为训练集和验证集，替代旧代码
（qinwc）的纯随机切分。

**收益**：
- 零 chain 级数据泄露：验证集中没有任何 chain 与训练集的 chain 在 30% identity 层面同源
- 训练采样权重：基于 40% identity 聚类计算 `weight ∝ 1/max_cluster_size`，每个同源簇的
  总采样概率相等，避免大簇主宰训练 batch
- 完全可复现：seed=42，所有中间产物落地，重新运行得到完全一致的结果

**参考**：AlphaFold-Multimer (Evans et al., *Nat Commun* 2023) 的 Dimer1193/Oligomer562
benchmark 构建流程 + Boltz-1 (Wohlwend et al., 2025) 的 MMseqs2 参数。

## 当前卡在哪

### 1. 训练代码尚未适配 identity sampling weights

`sampling_weights.pt` 已经生成好了，但 `_runtime.py` 的训练入口还没有用 `WeightedRandomSampler`。
旧代码用的是 uniform sampling。需要在一个地方加入：

```python
data = torch.load("sampling_weights.pt", weights_only=False)
weights = [data["sampling_weights"][cid] for cid in train_ids]
sampler = WeightedRandomSampler(weights, num_samples=len(weights), replacement=True)
```

具体插入位置取决于 PhysPPI 的 DataModule 实现。

### 2. split_manifest.json 路径有待训练环境验证

`precomputed_mesh/cli_v3/split_manifest.json` 的路径在训练节点上必须可访问。
确认方式：训练前 `ls` 一下或者 import 试一下。

### 3. Val 的 AFDB 代表性不足

AFDB 只有 6.9% 进了 val（686/10,000），而 Q-BioLiP 有 13.1%（1,316/10,021）。
原因是最大的同源连通分量主要由 Q-BioLiP 的实验结构组成——这些 PDB 结构之间的序列同源性
远高于 AFDB 的 AlphaFold 预测结构。AFDB 序列更"新颖"（单例/小 cluster 更多），
被"挤"到了 train。

这个不对称不影响数据泄露的保证，但如果将来需要在 val 中平衡评估 AFDB 和 Q-BioLiP，
可以考虑 per-dataset 分别做 split（代价是放松 chain-level homology 保证）。

### 4. 验证集数量可能偏多

2,002 个 val case 相对于业界标准（Boltz-1: 553/190k = 0.3%）偏多。
如果训练时发现 val loss 计算太慢，可以考虑进一步缩小 val（如 95:5 = 1,001 case）。

## 踩过的坑——绝对不要再踩

### 1. seq_cache 里的 chain 数量远超预期（最坑）

**预期**：20,021 个 complex，每个都是 dimer（2 chains），应该 ~40,000 条 chain。
**实际**：91,143 条 chain。因为 seq_cache.pkl 中的 `full_seq_1aa` 包含了原始 PDB/AFDB
complex 的**所有 chain**（如 ribosome 60+ chains），不只有 dimer 的两条。

这导致 MMseqs2 的输入是 91,143 条序列而非 ~40,000，聚类规模大了一倍。
生成的 30% cluster（9,083 个）和 40% cluster（10,278 个）都是基于**所有 chain** 的，
不是只有 interface chains。

**影响**：同源检测是保守的——多 chain complex 更容易和其他 complex 共享某些 chain，
导致更大的连通分量。但也意味着两个"只共享一条非 interface chain"的 complex
会被归为同源——可能过于保守。

**如果想修复**：在 `extract_sequences.py` 中只提取参与 interface 的 chain（需要
额外的 interface annotation 来判断哪些 chain 实际参与了 PPI）。

### 2. 连通分量可能巨大

最大分量含 6,265 个 case（~31%）。这是因为它包含了所有和某个常见蛋白家族（如
ribosomal proteins、MHC 等）有任一 chain 同源的结构。由于同源检测是 chain-level
的，一个 giant protein 可以在 PDB 里"串联"出巨大的同源家族。

**教训**：在做贪心分配前，先打印分量大小分布。如果 largest > val budget，那它
必然全进 train——这是正确的行为，不是 bug。

### 3. AFDB 和 Q-BioLiP 的同源冗余度完全不同

Q-BioLiP（来自 PDB）的实验结构序列冗余度远高于 AFDB（AlphaFold 预测结构）。
贪心分配时，最大的分量（优先进 val）会被 Q-BioLiP 主导。这导致两个数据集的
val 比例不完全一致（AFDB 6.9% vs Q-BioLiP 13.1%）。

**如果将来加新的数据集**：先把各数据集的序列冗余度分布跑一下，再决定是否
per-dataset 做 split。

### 4. MMseqs2 easy-cluster vs easy-linclust

IntPEMP identity pipeline 用的是 `easy-linclust`，我们用的是 `easy-cluster`。
两者的聚类结果不完全相同（linclust 更快但 cluster 边界可能有细微差异）。
两个都可以用，但要**保持一致**——不要在 30% 和 40% 之间混用两种模式。

当前选择 `easy-cluster --cluster-mode 2` 是因为 AF-Multimer/Boltz-1 用的是
`easy-cluster`。

### 5. `sampling_weights.pt` 只含训练集

`data["sampling_weights"]` 里只有 18,019 个训练 case 的权重，没有验证集的。
验证集不需要采样权重（uniform 评估即可）。如果将来 `datasets.val_ids` 里的 case
被当作训练 case 来查 `sampling_weights` keys，会 KeyError。
判断 `case_id in data["sampling_weights"]` 或查 `datasets.afdb/qbiolip.val_ids`。

### 6. `split_manifest.json` 是 JSON 不是 .pt

openfold3 的 `_runtime.py:1424` 用 `json.loads` 读 manifest，所以这个文件必须是 JSON
格式。`sampling_weights.pt` 才是 `torch.load` 的。两个文件路径不同，不要混淆。

### 7. `build_split.py` 是确定性的，但依赖 seed

给定相同的 `--seed`、`--val-ratio`、相同的 cluster TSV 输入，输出完全一致。
但 `split_components()` 在同一 size 的分量之间用 `random.Random(seed).shuffle`
来打破平局——所以改 seed 会改变哪些同 size 分量进 val。

### 8. case_id 格式在不同数据集之间不同

- AFDB: `AF-0000000065760170-model_v1`
- Q-BioLiP: `1a0s_1`（PDB ID + bio-unit number）

在 `chain_index.json` 和 `case_chains.json` 中通过 `seq_id`（`{case_id}|{chain_id}`）
来唯一标识每条 chain。不要假设 case_id 格式。

### 9. 重新运行 build_split.py 会覆盖之前的输出

`build_split.py` 不检查是否已经跑过——它直接覆盖。想保留旧结果的话要先
备份 `train_ids.json`, `val_ids.json`, `split_manifest.json`, `sampling_weights.pt`。
